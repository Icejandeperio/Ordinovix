## Regression and collateral checks
- Reach and leakage:
  - `reaches` and `reachesVisit` are used for every recipient except the owners list, which is by role. A helper receives only a task notification for a client they are assigned to.
  - Visit notifications to a helper go to the assignee only. The title has no client data.
  - Notifications are written under `store.org.id`, and the Worker store is org-scoped.
  - List and unread-count are `userId === user.id`.
- Wrapper behaviour: `withEvents` returns the command's value and rethrows its errors, so a refused command adds nothing. There is no `this.` use in `commands.ts`, so losing `this` is harmless. Nested wrapped calls cannot duplicate, because ids are checked against the store.
- `pushNew`: awaited when `c.executionCtx` throws (tests), `waitUntil` in production. A rejection is swallowed with `.then(() => undefined, () => undefined)`, so a failed push never fails a saved write. It runs only after a successful batch.
- Existing mock notification, U13 and U21 acceptance tests pass in the full gate.

## Advisory
1. Concurrent writes can collide. Two requests that each load the store before either commits, and that both derive the same `ntf-...` id (for example two different lines of one task received at once), make the second batch fail with `UNIQUE constraint failed: notifications.id`. That is a 500 and the second write rolls back (the version guard only catches the case where both touch the same record). A retry succeeds. Proposal: turn the notifications inserts in `plan()` into `INSERT OR IGNORE` (or catch that constraint and reload).
2. Add a Worker/API test for `visit_ready` and for an assigned visit, so criterion 4 is covered in both modes for all five types.
3. A task with no owner while `helpersCanAccept` is on notifies nobody for "Received, needs review". The spec's fallback is the organization owner. Proposal: fall back to the owners when there is no owner membership.
4. `captureEventState` and the visit-ready check run on every wrapped command. For each planned visit item they scan lines, authorizations and tasks, which is roughly O(planned visits x items x records). It is fine for one preparer's data but was not measured with a large store. A single `sendDuePushes` also scans the whole org's pending set, and two overlapping runs (cron and a write) could push the same row twice. Proposal: measure with a few thousand tasks, and mark `pushed_at` before sending or use a conditional update.
5. If a reason already ends in a period, the "Left without everything ready" body ends in two periods. Cosmetic.
