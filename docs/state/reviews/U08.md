## Advisory (non-blocking proposals)
1. Borderline regression to decide on: the client form's suggested code comes from the first letter of each word, so a name that starts with punctuation, e.g. `(Sunrise) Trading Co.`, suggests `(TC`. It saved on main and is now refused with an inline Code message (the user can correct it). Proposal: make `handleNameChange` use only letters/digits when building initials.
2. Methods classified NO_FREE_INPUT that do take free text or enums and are not validated: `memberships.update` (`name`, `role`), `savedViews.save` (`name`, `query`), `clients.importCommit` (CSV rows: names/codes), `tasks.openPeriod` plan, `prefs.save` (enums such as theme, textScale, dateOrder). Also partial coverage inside validated methods: `tasks.update` checks only `notes` (not `tags`, `paymentExpected`), `lines.update` checks `label`/`copies` only, `contacts.upsert` does not check `role`, `visits.updateItem` only `questions`, `visits.recordOutcome` does not check `nextAction`. Proposal: add schemas and move these entries into VALIDATED.
3. Double messages: the MutationCache handler in `src/main.tsx` tests `mutation.options.onError`, which is only set for hook-level options, not for `mutate(vars, { onError })` or for callers with their own try/catch plus `toast.error`. Result: a VALIDATION error from client-form-sheet, the contact/authorization/new-task forms and the mutateAsync dialogs shows both the inline message and a toast (observed for the client code). Harmless but noisy; the calendar reschedule also adds a generic "Failed to change task due date" next to the specific one. Proposal: skip the global toast when the caller handles the error (e.g. mark with `meta: { handled: true }`).
4. Order of checks: `memberships.invite` validates before the owner check, so a helper sending a bad invite gets VALIDATION, not FORBIDDEN (project rule: policy first). Also stricter than spec: contact notes capped at 300 (spec 12.3 says 500) while the textarea has no maxLength; spec 12.2 requires client code uniqueness, which `clients.upsert` does not enforce (it did not on main either).
5. Pre-existing bug seen while driving (not U08, same on main): `contacts.upsert` for a new contact drops `title`, `role`, `phoneE164`, `email` and `notes` (the create branch builds the record without them), so a contact added with an email shows an empty email when edited. Worth a unit.
