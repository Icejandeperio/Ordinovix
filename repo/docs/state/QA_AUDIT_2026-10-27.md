# Ordinovix — QA audit and refactor verdict

**Date:** October 27, 2026
**Commit audited:** `34fd1c5` (main, "fix(appearance): implement layout density styling engine…")
**Scope:** whole frontend on mock data, against `Inspirations/Ordinovix_Build_Spec_v2.md`
**Companion file:** `tests/acceptance/regressions.spec.ts` (13 failing tests covering 12 bug IDs)

---

## 1. Verdict

**No rewrite. One bounded hardening pass, done in Claude Code, before the backend starts.**

The foundation is sound and worth keeping:

- Strict TypeScript compiles with zero errors; the production build succeeds; all 118 unit tests pass.
- Screens go through hooks and the `Repositories` interface (no screen imports sample data), so the API can replace the mock without touching most screens.
- `src/domain/types.ts` and `rules.ts` follow spec v2 closely; the line-transition table, derived status, due states, authorization validity, period and due-date rules are correct.
- 69 routes × 3 configurations (owner desktop light, helper desktop, owner phone dark at 390 px) = 207 page loads: no horizontal overflow anywhere, and no console errors outside the visit Record and Summary pages.

What is wrong is concentrated in three places, and none of them is cosmetic:

1. **The signature visit flow loses data.** Recording outcomes crashes on reload, and "Finish visit" completes a visit without saving the outcomes.
2. **Several screens are facades.** They look finished but are hard-coded or do not save: Settings (most sections), Task templates, Audit log, Insights charts, the Welcome wizard.
3. **Rules and permissions live in the screens, not in the data layer.** The repository lets the owner complete a blocked task with no reason, and lets the helper act on clients he is not assigned to.

Items 1 and 3 are exactly what the backend must get right, so fixing them now in the mock turns the mock into an executable specification for the API.

## 4. Process findings

1. **"Verified by browser subagent" is not evidence.** `PROGRESS.md` records browser verification for milestones that contain B01 and B02. Agent-asserted QA missed a crash in the product's signature flow.
2. **The governance in `AGENTS.md` is not running.** `docs/state/features.json` tracks only M0; `tests/acceptance/` does not exist; `docs/architecture/*` files it references do not exist.
3. **The verify gate cannot catch these bugs.** `scripts/verify.ps1` runs typecheck, unit tests and build. None of them renders a page.
4. **The gate is Windows-only.** `verify.ps1` and `init.ps1` will not run in Claude Code's Linux environment.

Fix: add `npm run lint` (with `react-hooks/rules-of-hooks` as an error), `npm run test:e2e` (Playwright), and `npm run verify` that runs typecheck, lint, unit tests, build and e2e. Keep the `.ps1` scripts as thin wrappers.

## 5. The refactor, precisely

Do these four things. Do not refactor anything else before the backend.

| # | Refactor | Why | Size |
|---|---|---|---|
| R1 | **`src/domain/policy.ts`**: pure functions `canAccessClient(membership, clientId)`, `requireOwner(membership)`, `canSetStatus`, `canTransitionLine`, `canFinishVisit(items)`, `canComplete(task, evidence)`. Every mock repository method calls them first and throws typed errors (`FORBIDDEN`, `NOT_FOUND`, `RULE_VIOLATION`) | One enforcement point that the Worker API reuses unchanged; fixes B02, B04, B11 at the root | M |
| R2 | **Zod at the repository boundary**: each write method parses its input with the schema from `schemas.ts` | Same validation in mock and API; fixes B16 without rewriting forms | S |
| R3 | **`<QueryState>` wrapper** for loading, error (with Retry, 403 and 404 variants) and empty, applied to every page | Fixes B03, B10, B13; required before real network failures exist | S–M |
| R4 | **De-facade**: Settings (split the 1,870-line page into one component per section, each wired to its repository method), Task templates, Audit log, Insights (compute from `metrics.ts`), Welcome | Fixes B06, B07, B08, B20, B30 | M–L |

Leave alone for now: the 3,453-line `src/data/mock/index.ts`. It becomes the test double once the API exists; splitting it now is effort with no user-visible return. Its behaviour, after R1 and R2, is the contract the API must match.
